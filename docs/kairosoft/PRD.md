## 1. 背景与问题

### 1.1 现状

当前游戏界面是「网页卡片式」DOM 渲染：

- **大厅**：预约清单列表页——顶部标题 + 患者卡片列表 + 右侧操作侧栏，无空间感，患者是一张张卡片而非「在诊所里的人」。
- **对话治疗**：聊天流 UI——左侧患者立绘 + 状态条，右侧聊天气泡滚动历史，底部选项按钮。
- **HUD**：顶栏文本状态条（等级/金钱/声望/理智/日期）。
- **设施**：`clinicUpgrades` 是 6 个字符串升级项，只改变数值与文字，无场景体现。
- **角色**：纯 CSS 手绘 Chibi 小人（`ChibiCharacter`），无任何位图资产。
- **资产**：仅 `public/images/clinic-bg.jpg`、`title-bg.jpg` 两张背景 + 1 首 BGM。

### 1.2 痛点

1. 诊所没有「空间」——经营感弱，患者与设施不存在于同一个可视空间里。
2. 对话治疗是「聊天软件」式，而非「面对面咨询」——叙事沉浸感打折。
3. 界面形态（卡片/聊天流/侧栏列表）与开罗式模拟经营的「场景驱动」范式差异大。

### 1.3 目标

将界面彻底重构为开罗（Kairosoft）模拟经营风格——参考《游戏开发物语》《温泉物语》《口袋学院物语》的布局、界面与交互范式。核心转变：

- **全量场景化**：经营层（大厅俯视场景）与叙事层（诊室面对面对话）都进入可视空间。
- **开罗式交互**：点选导航、点击对象弹菜单、底部菜单栏、顶栏常驻数值。
- **温暖手绘风保留**：沿用现有色板与美术语言，非像素化。

## 2. 目标与非目标

### 2.1 目标

| 目标 | 描述 |
| --- | --- |
| 俯视大厅场景 | 诊所大厅 2D 俯视，患者小人坐着候诊、走动，设施在场景中有可视化位置 |
| 可见医生 + 点选导航 | 医生小人在场景中，点地面/设施/患者自动走过去触发交互 |
| 诊室面对面对话 | 治疗在诊室场景发生，医生与患者相对而坐，逐句气泡，右上角可回顾 |
| 设施装修模式 | 进入装修模式可拖动设施重排位置（位置仅视觉，不影响数值） |
| 开罗式 HUD 与菜单 | 顶栏常驻核心数值，底部图标菜单承载全部功能入口 |
| 全量界面统一 | 信件/成就/技能树/发现客户/结局等全屏面板视觉开罗化，移除旧 DOM 大厅/对话 |
| 程序绘制资产 | 场景/设施/小人全部按 palette 程序绘制，零外部美术依赖 |

### 2.2 非目标（本版本明确不做）

| 非目标 | 说明 |
| --- | --- |
| 像素画风 | 保持温暖手绘风，非 16bit 像素 |
| 摆放影响数值 | 设施位置仅视觉，不影响动线/效率/覆盖等数值 |
| 家访场景 | 回访仍在现有界面发生，患者家中场景后置 |
| 开罗式经营评定 | 年结清算/最高分/二周目继承，后置 |
| 多周目 | 不做 |
| 原生 App / 移动端新形态 | 桌面 Web 为主，响应式基本保障（见 SPEC） |

## 3. 用户体验目标

### 3.1 玩家旅程

1. 进入大厅 → 看到诊所俯视全貌：候诊区患者小人坐着等待，前台助理走动，设施分布各处。
2. 点击一位患者 → 医生自动走过去 → 场景切到诊室，两人相对而坐。
3. 治疗中 → 说话者头顶冒气泡逐句推进，底部选项可点，右上角小窗可翻对话回顾，患者四维状态条常驻。
4. 治疗结束 → 回大厅，患者记录更新。
5. 点击设施 → 弹操作面板（查看/升级/装修）。
6. 点「装修」→ 进入装修模式拖动设施到网格位置。
7. 底部菜单栏 → 一键打开技能树/消息/追踪/成就/发现客户等面板。
8. 顶栏 → 等级/金钱/声望/理智/日期永远可见，数字随经营跳动。

### 3.2 设计基调

- **温暖治愈**：暖色主调、柔和圆角、无压迫感——开罗的「明快高自由」与本作的「治愈叙事」平衡。
- **场景即信息**：患者等待天数、情绪、状态尽量在场景里可读（头顶状态图标/颜色），减少跳转。
- **文本可读性优先**：对话是核心玩法，任何场景化不得牺牲气泡/选项/记忆碎片的可读性。

## 4. 设计决策记录（grill-me 共识）

> 以下 9 项经逐题共识锁定，SPEC/PLAN 必须遵循。

| # | 决策点 | 结论 | 理由 |
| --- | --- | --- | --- |
| 1 | 重构范围 | **全量场景化**（经营层 + 叙事层都进场景） | 用户明确要求，对话做进场景面对面 |
| 2 | 视觉风格 | **温暖手绘风保留**（非像素） | 保持现有治愈美术语言，不做像素化 |
| 3 | 技术分工 | **Phaser 场景 + React UI 覆盖层**，EventEmitter 桥接 | 符合 Phaser+React 最佳实践，现有组件复用 |
| 4 | 场景结构 | **大厅 + 诊室**双场景 | 大厅承载经营，诊室承载对话，家访后置 |
| 5 | 医生控制 | **可见 + 点选自动导航** | 保留开罗小人活动观感，免频繁微操 |
| 6 | 设施摆放 | **装修模式半自由**（位置仅视觉） | 保留摆放乐趣，避免平衡复杂度 |
| 7 | 资产方案 | **全程序绘制**（Phaser Graphics 按 palette 生成） | 零外部依赖、风格统一、可迭代替换 |
| 8 | 分期 | **五期 M1-M5**，每期独立可玩可提交 | 风险隔离，工程量大需拆细 |
| 9 | 对话形态 | **面对面逐句气泡 + 右上角对话回顾小窗** | 沉浸式咨询感，历史可查 |

## 5. 开罗特征 → 本游戏映射

| 开罗特征 | 本游戏现状 | 开罗化方案 |
| --- | --- | --- |
| 常驻顶栏数值（金钱/人气/日期） | 文本状态条 | 开罗式顶栏：等级/金钱/声望/理智/日期/时段，数字跳动 |
| 中央俯视经营场景 | 预约清单列表 | Phaser 大厅场景：候诊区/诊室/休息室/花园，患者小人候诊走动 |
| 设施自由摆放 | 字符串升级列表 | 设施可视化在场景中，装修模式拖动重排（位置仅视觉） |
| 点击对象弹菜单 | 点击列表卡片 | 点击场景中的患者/设施 → 弹出操作面板 |
| 底部菜单栏 | 右侧侧栏列表 | 开罗式底部图标菜单：技能/升级/消息/追踪/成就/休息/发现 |
| 小人在场景穿梭 | 无角色移动 | 医生点选导航自动行走；患者进入/离开/候诊动画 |
| 面对面对话 | 聊天流 | 诊室相对而坐，逐句气泡，右上角回顾 |
| 明快高自由、无硬失败 | 已有（无失败条件） | 保留：金钱可负、无 Game Over |
| 像素/Q 版画风 | 暖色手绘风 | **保持暖色手绘**（用户决策，非像素） |
| 经营评定/二周目 | 无 | 后置（非目标） |

## 6. 范围边界

### 6.1 保留不动（数据层零改动）

- `lib/data/`：patients / skills / truths / discovery / psychTerms / achievements / sceneBuilder / generator
- `lib/engine/`：DialogueEngine / AchievementEngine
- `lib/state/GameState.ts` + `lib/store.ts`（zustand 单数据源）
- `lib/state/Storage.ts`（存档格式 v1.0 兼容）
- `lib/audio/SoundManager.ts`
- 全部玩法规则：接诊/四维/技能/升级/获客/回访/结局/成就/信件

### 6.2 重建（视觉与交互层）

- `components/game/ClinicHall.tsx` → Phaser 大厅场景
- `components/game/DialogueScene.tsx` → Phaser 诊室场景 + React 覆盖层（气泡/选项/状态条/回顾窗）
- `components/game/HUD.tsx` → 开罗式顶栏
- `components/game/ClinicUpgrades.tsx` → 场景设施升级面板 + 装修模式
- 各全屏面板（技能/消息/追踪/成就/发现客户/结局/信件）视觉开罗化
- `ChibiCharacter`（CSS）→ 程序绘制小人（Phaser Graphics 版 + 场景外复用 DOM 版）

### 6.3 新增

- `components/game/phaser/`：Phaser Game 实例、场景类（大厅/诊室）、小人/设施/装饰程序绘制模块
- `lib/bridge/`（或同类）：React ↔ Phaser EventEmitter 桥
- 装修模式交互、点选导航寻路

## 7. 成功指标与验收

1. **每期独立可玩、独立提交**——M1–M5 各阶段结束游戏可运行、可验证、可回滚。
2. **存档兼容**——v1.0.0 新版本可读取旧存档（`ps.save.v1`），数据层零改动。
3. **现有测试保持通过**——vitest 全部用例（含 GameState / sceneBuilder）不因重构失败。
4. **数据层零改动**——`lib/data`、`lib/engine`、`lib/state` 重构期间不因界面需求修改（除必要时纯新增）。
5. **文本可读性不降级**——对话/选项/记忆碎片在场景化后依然清晰（SPEC 硬约束）。
6. **玩法等价**——重构后所有既有功能（获客/升级/回访/结局/成就）行为一致，仅呈现方式变化。

## 8. 风险与缓解

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| CSS Chibi → Phaser Graphics 程序绘制表达力不足（表情/动画） | 中 | 简化走动物理动画（位移/晃动），静态立绘保留 DOM Chibi 复用；可迭代替换 |
| React overlay 与 canvas 的 z-index/遮挡问题 | 中 | 分层规范：canvas 基底 + overlay 绝对定位 + portal 弹窗顶层（沿用现有 createPortal 经验） |
| 每帧全量同步 store 导致性能问题 | 中 | Phaser 只读 store、事件驱动同步；禁用每帧轮询，变更通过事件/回调推送 |
| 点选导航寻路（障碍/碰撞） | 中 | 网格化简化寻路（A* 或网格步进），场景障碍物少量且固定 |
| 程序绘制场景表现力 vs 现有手绘背景 JPG 拼接 | 低 | 背景 JPG 作基底 + 程序绘制元素叠加，色板统一 |
| 响应式/移动端 canvas 缩放 | 低 | Phaser Scale 模式 + 覆盖层 rem 布局，小屏菜单重排 |
| 工作量巨大、长周期 | 高 | 五期拆解 + 每期独立提交回滚 + 每期验收 |
